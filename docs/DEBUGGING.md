# Debugging and session audio

## Why audio capture exists

Text logs are not enough for full-duplex audio problems. A slow or broken turn can come from different layers:

- microphone routing;
- wake-word timing;
- activation cue masking speech;
- VAD not closing the user turn;
- provider reconnect;
- slow or incorrect tool calls;
- irregular provider PCM delivery;
- playback buffering;
- acoustic echo and false interruption.

The recorder keeps multiple synchronized representations so these layers can be separated.

## P610 session files

A recorded session can contain:

### mic_raw.wav

The physical microphone signal captured by the local transport. Use it to inspect room noise, echo, clipping, and whether the command was actually captured.

### gemini_input.wav

The audio that passed the local wake gate and was forwarded toward Gemini. Compare this with mic_raw.wav to see whether wake/cue buffering removed or delayed speech.

### assistant_raw.wav

Audio frames generated by Gemini before the physical playback path.

### assistant_played.wav

Audio successfully written to the P610 playback path. Compare with assistant_raw.wav to identify local-output loss.

### mix_stereo.wav

A synchronized diagnostic mix with microphone and assistant on separate stereo channels. It is useful for seeing whether the P610 microphone hears a strong delayed copy of the assistant.

### timeline.json

Structured timing events such as:

- capture_started;
- wake;
- wake_cue_started / wake_cue_skipped / wake_cue_finished;
- first_assistant_audio;
- PCM gaps;
- provider interruption;
- Stop;
- provider error;
- TTS stopped;
- session closed.

## Retention

Debug recordings default to 24-hour retention. Cleanup runs periodically, not only when a new conversation starts.

This is intentional: recordings can contain private room audio and should not become a permanent archive.

## Latency analysis

For a slow response, calculate or inspect these phases:

1. wake to end of user speech;
2. end of user speech to transcript/turn completion;
3. turn completion to first tool call;
4. tool-call duration;
5. final tool result to first assistant PCM;
6. first raw PCM to physical playback start;
7. inter-frame gaps during playback.

A high wake-to-first-audio number alone does not identify the bottleneck.

## Common signatures

### Command masked by activation cue

Symptoms:

- wake detected;
- cue starts almost immediately;
- gemini_input contains silence or only a fragment of the intended command;
- transcript is unrelated or appears much later.

Fix direction: increase the cue-decision window or skip the cue on continuation.

### VAD holds the turn open

Symptoms:

- user finished speaking;
- mic contains intermittent low-level speech-like bursts;
- transcript/turn completion occurs many seconds later.

Fix direction: inspect microphone noise/echo and end-of-speech tuning. Do not simply shorten every timeout without checking the waveform.

### Tool detour

Symptoms:

- transcript is wrong or ambiguous;
- model calls an unrelated Home Assistant tool;
- one or more tool errors occur before response audio.

Fix direction: improve input recognition, compact/clarify tool schemas, and remove invalid tool argument shapes.

### Provider/network PCM gaps

Symptoms:

- assistant_raw has discontinuous frame timing;
- runtime reports many gaps above 200 or 500 ms;
- assistant_played follows the same gaps.

Fix direction: investigate Gemini proxy/network path rather than P610 output.

### Local playback issue

Symptoms:

- assistant_raw is continuous;
- assistant_played is missing frames or output process errors are logged.

Fix direction: inspect pacat/PulseAudio routing and output process health.

### Self interruption / echo

Symptoms:

- provider interruption appears while assistant speech is active;
- mic_raw contains assistant audio;
- there is no meaningful user utterance.

Fix direction: acoustic echo control, physical volume/layout, or more robust interruption gating.

## Privacy rules

Do not publish session recordings in issues without reviewing them first. A stereo mix can include private conversations, wake-word false positives, and background audio that was never intended for the model.
