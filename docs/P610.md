# Plantronics P610

## Goal

The P610 path turns a USB Plantronics speakerphone into an always-ready Home Assistant voice endpoint while keeping the same Gemini Live and MCP flow used by the browser client.

Desired interaction:

    Okay Nabu, what is the weather?

The user should not need to wait for an activation sound between the wake phrase and the command.

## Audio routing

The main add-on requests host audio access. The P610 should resolve as the desired default capture and playback device, or the host PulseAudio configuration should map default to the P610.

Use the optional P610 Microphone Monitor add-on when diagnosing:

- no microphone signal;
- wrong capture device;
- unexpected input level;
- muted microphone;
- channel/sample-rate problems.

## Home Assistant speaker-volume control

The planned P610 Home Assistant entity is intentionally volume-only. It should expose the PulseAudio sink already used by Pipecat/pacat so Home Assistant can read and change speaker volume and mute state.

Supported controls should be limited to:

- volume level readback;
- volume set;
- volume up/down;
- mute/unmute.

The entity must not expose play, pause, stop, play_media, TTS, source selection, media browsing, or any other action that can start audio. Calling a volume or mute service must only change the PulseAudio sink state; it must never inject audio, open a playback stream, restart Pipecat/Gemini, or otherwise cause the P610 to make sound by itself.

Assistant speech still reaches the P610 through the existing Pipecat -> raw PCM -> pacat -> PulseAudio path. The Home Assistant entity only changes the output gain of that already-existing path.

Microphone gain remains a separate setting and is not tied to speaker volume.

## Local wake word

The current bundle includes microWakeWord models for:

- Okay Nabu;
- Stop.

The wake detector runs locally. In standby, microphone PCM is not sent to Gemini.

Default wake confidence:

    0.6

Default Stop confidence:

    0.5

Raise a threshold if there are false detections. Lower it carefully if the intended word is frequently missed.

## Continuous command handling

The runtime keeps a local pre-roll ring and, after wake detection, retains a short trailing overlap. It then waits briefly to see whether speech continues.

If speech continues:

- the wake cue is skipped;
- buffered command audio is flushed to Gemini;
- full-duplex streaming continues.

If the user pauses:

- the wake cue is played;
- cue echo is not forwarded as user speech;
- the next command starts cleanly after the cue.

This avoids the common failure mode where the activation beep masks a short command such as weather.

## Warm provider session

The Gemini Live session is connected and context-primed before wake when possible. This removes the provider connection handshake from the normal wake path.

The warm session still experiences provider-managed idle WebSocket rotation. The runtime reconnects automatically.

The current P610 path also monitors the private Gemini realtime-input readiness latch. If wake occurs while that latch is false, microphone frames remain buffered while the runtime first waits briefly for the normal reconnect and then, if necessary, forces a reconnect of only the P610 Gemini service. If readiness still cannot be restored, only the P610 worker is recycled; Home Assistant Core and browser/WebRTC workers are left alone.

Activation-buffer overflow is tracked explicitly and cleared when the buffer is drained or the turn/session is reset, so one delayed provider recovery does not leave a permanently degraded status flag.

## Model-driven conversation end

Local `Stop` remains the fastest hard stop, but the active P610 flow also exposes an `end_conversation` tool to Gemini. The model should call it only when the user's meaning and context clearly request ending the current voice conversation/listening session.

The tool does not use a fixed phrase list. It is intentionally distinct from requests such as stopping music, a timer, ventilation, or another Home Assistant device.

After an accepted model-driven end request, the runtime lets Gemini play one short farewell, then closes the P610 conversation, plays the end cue and immediately warms a fresh standby worker.

## Thinking cue

The P610 flow exposes a small `thinking_signal` tool for work that is expected to leave the user waiting because of search, several tool calls or nontrivial analysis. It plays a short local nonverbal cue and should not be used for simple direct commands such as turning a known light on or off.

## P610-specific VAD

The physical path currently prefers fast short-command completion:

- Gemini server VAD remains enabled;
- end-of-speech sensitivity is high;
- silence duration is around 350 ms.

This is intentionally separate from browser VAD tuning.

## Full duplex and interruption

Once active, microphone audio continues to flow while the assistant is speaking so the user can interrupt the response.

Because the P610 contains a speaker and microphone in the same device, acoustic echo can still affect provider VAD. If the assistant appears to interrupt itself, inspect the session mix and provider-interruption timeline before increasing thresholds blindly.

Useful checks:

1. Does mic_raw.wav contain a strong copy of the assistant voice?
2. Did Gemini emit an interruption event while assistant audio was playing?
3. Was there a real user utterance in the microphone channel?
4. Did the transcript contain random short Latin/Korean/other-language garbage?

## Playback path

Streaming assistant PCM is written to pacat with a small PulseAudio buffer. This is intended to smooth irregular network chunk delivery while preserving low latency.

The runtime measures:

- first assistant audio after wake;
- gaps above 100 ms;
- gaps above 200 ms;
- gaps above 500 ms;
- maximum gap in the response.

A normal end-of-stream appends a short silent tail before closing the PCM stream so the P610/PulseAudio stack has time to play the final phoneme.

## Stop behavior

Stop is detected locally while the conversation is active.

A Stop event:

- interrupts the current assistant output;
- plays the end cue;
- closes the current realtime worker;
- immediately creates and warms a fresh standby worker.

This is different from a provider failure and should not increment the error-retry backoff.

## Recommended acceptance test

Run this test after any change to wake logic, VAD, provider configuration, audio routing, or Pipecat version:

1. Wait until standby_state is ready.
2. Say a single continuous phrase:

    Окей Набу, какая сегодня погода?

3. Do not pause after Nabu.
4. Confirm the wake cue is skipped.
5. Measure wake-to-first-audio latency from timeline.json.
6. Confirm the transcript matches the intended command.
7. Check tool-call count and tool errors.
8. Confirm assistant_played.wav ends cleanly.
9. Say Stop while the assistant is speaking and verify immediate interruption/recycle.

## Wake/AEC development workflow

The confirmed `включи свет` -> `чи свет` activation-cue truncation is tracked as a separate incremental engineering project.

Sources of truth:

- [P610 Wake/AEC Development Plan](P610_WAKE_AEC_DEVELOPMENT_PLAN.md)
- [P610 Wake/AEC Development Log](P610_WAKE_AEC_DEVELOPMENT_LOG.md)

Do not rely on chat history alone. Any scheduled/hourly Home Assistant maintenance pass that advances this work should first read the plan and latest dev-log entry, perform only the smallest safe unblocked step after health-critical work, test it, and append the result, rollback information, blocker and exact next action to the development log.

The long-term invariant is stricter than the legacy `cue_playing` behaviour described above: local playback may be acoustically cancelled, but user microphone frames must not be discarded merely because the P610 is playing its own activation cue or TTS.
